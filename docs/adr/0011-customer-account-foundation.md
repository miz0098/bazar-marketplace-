# ADR 0011 — F12 customer account and wishlist foundation

Status: persistent local demo wishlist and isolated PostgreSQL/HTTP customer foundation. Not real account authentication, verified-purchase publication or production readiness. Base is merged PR #22, d89bd6e0cf1fba66b2de34f12068a184f08739dd.

## Local demo wishlist

F12 explicitly supersedes F11's reset-on-refresh wishlist requirement. The existing account mock remains the ready-store; a persistence decorator stores only `{version:1, productIds:string[]}` under `bazar-demo-wishlist-v1`. It never serializes profile, recipient data, product price/title/stock, phone, auth flags, tokens, message/review text or payment values. Known IDs resolve through current immutable demo catalog data on restore. Unknown removed products disappear; unavailable known products remain visible/removable with cart action disabled. IDs are bounded/deduplicated, schema/version/extra keys and a 16 KiB/200-ID limit are checked. Corrupt payloads are discarded and replaced with a safe empty record; failures show a warning and retain a usable in-memory preview without claiming account persistence.

The external observable service and useSyncExternalStore synchronize card/detail/header/account list. Root effects connect storage and subscribe to same-origin storage events; no timer is used to manufacture React effect updates. Cross-tab changes reload canonical IDs without copying another tab's product fields or echo-writing valid storage. Local concurrent writes have browser last-write-wins semantics; this is not a production merge algorithm. Explicit empty lists survive reload. A missing initial record preserves the historical E1 seeded demo list; restored ordering follows the ID list, with synthetic internal sort dates rather than invented real account history. The wrapper has an immutable initial server snapshot to avoid hydration mismatch. Buttons wait for restoration; completed mutations, rather than pending simulated requests, are the persistence boundary.

Profile/address/review edits and communication remain existing in-memory preview services. Their personal fields are not persisted by the wishlist wrapper. Legacy courier-address preview stays local; no automatic conversion to the server carrier contract exists. Ukrposhta is added to the existing address selector without redesign; it advertises a branch, not an unsupported locker. Existing sidebar remains orders, wishlist, messages, reviews, personal data, addresses, payment methods, support and exit. No Overview navigation section is added; the approved existing /profile landing is preserved.

## Isolated server service and routes

createCustomerService requires NODE_ENV=test; createApiServer independently rejects customer injection outside test config. Main constructs neither customer nor review-policy adapter. Ordinary /api/v1/customer and /api/v1/wishlist routes fail 503 without cookies. No environment toggle bypasses F4 SMS/session restrictions. Success DTOs explicitly say mode:integration-test; private reviews say publication:not-asserted. Existing /users/me and auth logout/session APIs remain separate.

All successful operations use the verified F4 server principal, exact Origin/Fetch Metadata and CSRF for mutations; caller user IDs/unknown keys/queries are rejected. JSON/body/time bounds, HttpOnly/Secure/SameSite cookies, sanitized failures and static request labels are reused. No credentialed CORS, browser-readable bearer token, real PII import or provider activation is introduced.

- GET/HEAD /api/v1/wishlist: own current DB product summaries, current min variant price/availability; null price and unavailable when no variants. PUT/DELETE /wishlist/items/{productId}, body `{}`, are idempotent owner-scoped add/remove. Unavailable products can stay wished; no cart reservation or price guarantee is implied.
- GET/HEAD/PATCH /api/v1/customer/profile: only id, firstName, lastName and version. PATCH requires expectedVersion and both bounded names. No phone/email/birthday/gender/consent update or contact recovery is inferred from the richer preview form.
- GET/HEAD/POST /customer/addresses; PATCH/DELETE /addresses/{id}; PUT /addresses/{id}/default. Only carrier, ASCII opaque cityRef/locationRef and explicit isDefault are accepted. Updates/deletes/default changes require expectedVersion. No recipient name/phone/street, delivery guarantee, live directory validation or address UI mapper is supplied.
- GET/HEAD/POST /customer/reviews; PATCH/DELETE /reviews/{id}. Owner-only private reads, runtime rating/text validation, owned source order line and explicit isolated policy gates apply. No public review/list/rating/moderation API is activated.

Parameterized SQL, per-actor user-row locking, scoped row predicates and version checks serialize mutations. Defaults mean at most one, chosen explicitly; setting one clears/increments versions of other defaults. Deleting a default leaves none rather than inventing replacement rules. Referenced address deletion fails 409 through restrictive FKs, with rollback; no implicit checkout/order reassignment. Existing preview auto-default behavior is not silently promoted into production policy. Lists are bounded at 100; overflow fails closed instead of truncating. Pagination, runtime roles/grants, rate/capacity/retention and activation still require review. Technical limits are not production business defaults.

## Review eligibility, duplicate protection and deletion

F12 does not decide what constitutes a confirmed purchase. An explicit `scope:isolated-test` policy must attest a known **owned** order line with a bounded synthetic proof; there is no default allow. F6/F9 integration-mode orders are rejected even if an injected test policy claims confirmation: signed synthetic payment success is not a real purchase. The browser cannot submit verifiedPurchase, status, publication, owner or product overrides. Product identity is derived from the owned DB line. The future real resolver must use approved authoritative purchase/return/fulfillment rules; none is selected here.

Edit/delete additionally require explicit policy permission and a matching F12 claim. Legacy unproven reviews are readable privately but are not rewritten through this foundation. Test edits do not publish reviews. An allowed test deletion removes review text while retaining an immutable test purchase claim; repeated creation for the same line conflicts even after deletion. This tests a conservative anti-duplication boundary, not a production moderation/edit-window/retention decision. Those rules must be approved before any live mutation.

Additive migration 0011 introduces profile/address versions and review_foundation_claims, with source-line/owner/product FK, unique line/review IDs, SHA-256 proof digest, integration-test mode, owner index and immutable trigger. The receipt contains no raw proof or review text. Existing review UNIQUE(order_line_id) also guards concurrent duplicates. Review and claim insertion are one transaction; failed claim persistence rolls back review text and permits retry. Prior migrations 0001–0010 are unchanged.

## Client and activation limits

CustomerBusinessClient is a separate opt-in same-origin typed transport: browser-managed cookies, closure CSRF, bounded bytes/time, no redirects/cache/retries/demo fallback, strict DTO/resource validation and mutation result correlation. OpenAPI 1.8 documents exact paths/inputs/scopes. No existing preview provider selects it; demo string IDs are never automatically mapped/merged to PostgreSQL UUIDs.

Blockers: production SMS/provider/keys/rate/retention/proxy/BFF/TLS and browser session rollout (ADR4); real name/contact/recipient encryption/key rotation/consent/version/retention/deletion and phone re-verification; address authority/carrier validation/pagination/concurrency UX; purchase eligibility/refunds/moderation/publication/edit/delete/abuse/retention policies; typed UI/server mapping and production role grants/operational release. Plaintext schema names are used only by disposable synthetic tests under this composition, not authorized real-PII storage. Saved payment methods remain safe empty demo; no PAN/CVV/provider binding is added.
