# Full Functional Simulation — F24 baseline

Audit: origin/vps-migration is 8080264 (F24). The supplied work checkout contained F25; no F25/F26 source is used. Existing F4/F15 authentication, F21 cart/wishlist, F22 checkout/payment and F24 account/communications remain authoritative. Production entry is unchanged.

Implementation plan: reuse the isolated HTTPS storefront and PostgreSQL composition, add an interactive simulation launcher, server-owned payment settlement and an owner-bound code inbox. Present ordinary Ukrainian operation/success/error screens. Keep synthetic-only adapters, loopback binding, Secure HttpOnly cookies, exact Origin/CSRF, signed observations, ownership checks, idempotency and rate limits. Do not create a parallel commerce implementation or activate real providers.

The database is isolated per run. Successful mutations survive navigation, refresh and logout within that run; stopping the disposable runner removes its database. Only invented personal information is allowed. No SMS, real card data, real money, carrier dispatch or deployment.

## Запуск

Требуются Node 24, Docker/Compose и OpenSSL. Установить зависимости:

```sh
npm ci --prefix apps/api
npm ci --prefix apps/storefront
npm ci --prefix tests/e2e
npm run simulation:start
```

Команда собирает отдельную витрину, запускает PostgreSQL и печатает локальный HTTPS URL и путь к краткоживущему сертификату. Для ручного браузера требуется доверие именно этому локальному сертификату; проверка TLS не отключается. Playwright использует точное SPKI-сопоставление сертификата, сохраняя `ignoreHTTPSErrors: false`. Завершение Ctrl+C останавливает сервисы и удаляет базу этого запуска. Отдельные запуски не делят пользователей, сессии, заказы или ключи.

`npm run simulation:test` запускает desktop/mobile сценарии с реальной PostgreSQL. Для проверки отказов при ручном запуске можно задать `BAZAR_SIMULATION_PAYMENT_OUTCOME=declined`, `pending` или `unknown`; по умолчанию используется `succeeded`. Исход задаётся серверу при старте, не браузером. `BAZAR_SIMULATION_STEP_MS` задаёт шаг жизненного цикла от 1000 до 60000 мс; обычный запуск — 15000 мс, автоматические проверки — 1000 мс.

## Реализованное поведение

- Регистрация, вход по случайному одноразовому коду, повторный код, выход и повторный вход. Код доступен только своему challenge/flow после Origin/CSRF-проверок; фиксированного универсального OTP нет.
- Корзина и обране используют серверные записи. В этом режиме добавление в гостевую корзину требует входа: локальная запись больше не выдаётся за сохранённую серверную операцию. Автоматического переноса гостевого содержимого нет.
- Оформление с выбором конкретных предложений и доставки для каждого продавца, промокодами, неизменяемыми денежными снимками и защитой повторных запросов. Успех оплаты появляется только после подтверждения серверным адаптером и транзакцией commerce. «Дякуємо за замовлення!» сохраняется при обновлении страницы; заказ остаётся в кабинете после выхода и нового входа.
- Профиль, адреса, настройки уведомлений и обращения о персональных данных используют F24. Добавление синтетического платёжного метода — отдельная серверная capability, выключенная по умолчанию. Создаётся только masked reference без ввода/приёма PAN/CVV; выбор основного и удаление сохраняются с прежними проверками владельца и версии. Повтор запроса после удаления не восстанавливает метод.
- Фоновый процесс работает только в изолированной композиции. Подготовка заказа выполняется от сгенерированного владельца продавца; доставка проходит через подписанные транспортные события. Запрос отмены, приём возврата и возмещение используют F23, включая прежние ограничения финансовых правил. Реальных отправлений или возврата денег нет.
- Отзывы требуют подтверждённой покупки. Синтетическая модерация, ответы на вопросы, сообщения продавца и поддержки проходят существующие capability/membership проверки, сервисы и аудит. Поддержка получает явное назначение на конкретное обращение. Ответы являются автоматическими ответами симулятора, не общением с реальными людьми.
- Диалоги обновляют входящую историю автоматически; сохранённые сообщения и предыдущие страницы истории сохраняются. Статусы заказов также обновляются в открытом кабинете. Уведомления остаются внутренними записями БД.
- В этом режиме убраны пользовательские подписи Demo/Mock/Preview и технические тестовые подписи на основных экранах, в каталоге, информации, уведомлениях и истории. Исходные диагностические подписи сохранены для прежнего acceptance-режима; production-композиция не переключается на симулятор.

## Сохранённые ограничения

Используются только вымышленные данные и синтетический каталог. База сохраняет успешные изменения в течение запуска, включая навигацию, refresh и logout/login; после остановки disposable-база удаляется. Это не долговременное хранение между запусками.

Фото/вложения и изменение телефона остаются недоступны. Запрос удаления данных регистрируется, но не выполняет автоматическое стирание. Частичные возмещения, не разрешённые существующими финансовыми правилами, остаются заблокированы. Юридические страницы не подменяются вымышленными принятыми условиями. Real SMS, платежи, токенизация, email/push и интеграции отправлений не подключены. F25/F26 не восстановлены; Shopify-источник, production API, механизмы безопасности и схемы миграций не переписывались.

## Проверка

Результаты проверок приведены ниже. Ошибки промежуточных запусков исправлялись без ослабления утверждений, таймаутов, TLS, CSRF или владельческих проверок. Обнаруженное отсутствие автообновления входящих сообщений исправлено в UI; старые подписи найдены отдельным обходом обычных страниц. Один промежуточный legacy-browser запуск получил `ERR_NETWORK_CHANGED` при одновременном создании/удалении Docker-сетей другими наборами; итоговая проверка выполняется отдельно.
