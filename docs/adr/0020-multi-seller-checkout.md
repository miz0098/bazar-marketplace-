# ADR0020 — F22 multi-seller checkout and financial snapshots

Status: implemented isolated target protocol; financial rounding-mode decision PD-01 still pending. Base merged PR #32, `da77a976139dd01ec547075e890ac80e31797101`. Authority: explicit Phase F22 requirements; no live commerce approval. [Acceptance and limits](../F22_CHECKOUT_ACCEPTANCE.md).

## Compatibility boundary

F6/F8/F9/F14/F16 immutable single-line/test-quote protocols cannot safely express parent/seller components, carrier-managed shipping and the newly approved allocations. Preserve them and migrations0001–0017. Add migration0018 and `/api/v1/commerce/*`; reuse F4 sessions/Origin/CSRF, F20/F21 exact offers and active cart, F5 campaign/product eligibility tables and monetary validation, existing F7 shipping directory adapters, F8 PaymentAdapter/authenticated observations and F13 inbox. F22-enrolled campaigns are denied through the old F5 evaluator rather than misinterpreted under its one-line/stock rules. Old campaigns remain unchanged. Production main does not construct the new service; test-only injection is independently enforced.

## Financial policy

Use integer minor units and BigInt rational arithmetic throughout authoritative calculations. Compute one parent merchandise discount from eligible merchandise only, cap it to that basis, then assign proportional whole minor units and distribute remaining pennies by descending exact remainder with immutable variant/line UUID lexicographic tie-break. Array iteration order is irrelevant. Each seller's commission is independently 5% of its net merchandise; proceeds = net minus commission. Parent amounts equal sums of seller/line allocations exactly. No carrier amount, tax/processing fee, settlement or payout is invented.

The approved largest-remainder algorithm resolves allocation, **not** fractional percentage-total/commission rounding mode. F19 PD-01 still explicitly requires a product/finance choice. Active composition is `exact-only`: non-integral aggregate percentage or seller commission fails policy-required, never silently floors/rounds. Half-up and half-even functions are unit-tested alternatives, not activated policies. Zero-payable checkout needs an approved non-payment finality protocol (PD-04) and stays unavailable. Ambiguous minimum-order basis stays gated; scopes use explicit selected product/category IDs, with no implicit category-descendant expansion or seller-funded accounting.

## Transaction and provider boundaries

A quote freezes owned selected exact offers, quantities, versions, current prices, contact, each seller's independently selected verified pickup point and full financial calculations. It has owner/key/canonical-digest idempotency. Payment initiation locks the reviewed quote/current cart/catalog rows, revalidates prices/availability/promotion/location, atomically writes one parent, seller components, immutable lines, promotion and cart payment-exclusion claims and a durable attempt before any provider call. A stale quote requires new customer review; no higher amount is silently charged. Canonical hashing sorts object keys so PostgreSQL JSONB key order cannot invalidate identical plans.

The existing isolated provider adapter receives only the server amount/currency and durable attempt UUID. Submit exactly once; an uncertain/initiated operation must be inspected/reconciled, never blindly resubmitted. Only a verified definitive decline releases its claims and permits a new explicit attempt. Provider events bind operation/account/reference/amount/currency and event digest, deduplicate and reject terminal contradictions. Late events for an older declined attempt do not mutate a newer attempt's parent projection or claims. No browser redirect/success field can confirm payment.

Verified success is stored independently before retryable finalization. Finalization transaction updates parent/seller statuses, consumes the reserved promotion once, clears purchased cart units and emits one existing order-created event. A failed finalization leaves durable verified payment and recoverable unchanged cart/order projections; reconciliation retries without charging. Expired/modified promotion after authorization retains proof and enters verification-required, preserving cart and claims; resolution/refund is not invented.

## Cart and ownership

Migration0018 adds a generation UUID per physical cart row. Quantity additions retain generation; remove/re-add creates a new generation. Successful checkout subtracts its frozen quantity only from the same generation, removes exhausted rows and leaves newer/unselected rows intact. An actual cart mutation increments its optimistic version once in the same finalization transaction; replays do not increment again. These are cart units and payment-exclusion claims, not inventory quantities or warehouse reservations. Unavailable saved entries remain and cannot be selected for purchase. Quotes require explicit selected offers and one independently verified delivery per participating seller.

Owner-only parent reads; active seller membership yields only its own component/lines/financials, never siblings or complete parent contacts. Immutable snapshot/history/event triggers, composite FKs, unique checkout completion/unresolved attempts and deferred reconciliation guard transaction integrity. No PAN/CVV/card token is collected or stored. Only synthetic contacts are allowed in the isolated demo; production PII retention/encryption/grants remain gated.

## UI and lifecycle seams

Shared ordinary checkout now selects the server path only inside the F21 isolated entry. Default local demo is preserved. Same three steps/classes: contacts+per-seller delivery; card+one promo+server summary; confirmation only after parent confirmed and authoritative test success. Bank card remains; real wallet capabilities/provider unavailable, cash/installments not activated. Refresh stores only opaque quote/parent/idempotency references, never contact or financial authority. My Orders reads persisted parent/seller snapshots and factual history. F14 legacy return/refund protocols are preserved and deny unrelated F22 IDs; F23 must add a reviewed parent/seller/line/refund bridge and unit-discount attribution, not counterfeit legacy paid orders or commission retention.
