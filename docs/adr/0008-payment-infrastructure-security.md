# ADR 0008 — Phase F8 Payment Infrastructure & Security

Status: isolated PostgreSQL/HTTP protocol foundation. No payment provider, merchant, real charge, wallet session, legal payable amount or refund is activated. Based on merged F7 PR #18, c5f0e35e0cdaee9637644465fb33eaae4868c800. Ukrposhta is included in this same F8 PR; see ADR 0009.

## Financial boundary

F5 evaluates exact merchandise promotions, F6 retains payableTotal:null and delivery/payment not initiated, and F7 returns a non-binding test shipping estimate. They do not define tax, fees, seller allocation, inventory commitments, legal orders or a payable total. Adding merchandise and shipping automatically, or copying the browser's demo total into a charge, would invent financial policy.

Use an explicit server-only **isolated-test-plan** callback to supply a synthetic amount/revision for protocol tests. Persist its binding to the verified owned checkout pricing fingerprint. It is not a production financial calculator, reservation, invoice or order payment. The public input contains only checkoutId, expectedVersion, method and idempotencyKey. Never accept caller amount/currency/user ID, PAN/CVV, payment or wallet credentials/tokens, provider status, merchant data, redirect/return URL or alleged browser success. Production amount derivation remains unavailable until approved authoritative order/payment contracts exist.

The constructor requires NODE_ENV=test and an isolated-test adapter; the HTTP server independently rejects injection outside its test environment. Main constructs neither. All /api/v1/payments paths, including webhooks, return 503 in ordinary runtime. No env flag enables test payment success in production. Tests/helpers contains the only synthetic HMAC implementation and is excluded from the build. There is no selected gateway, API key, hosted page, provider SDK, paid service or payment form collecting card details.

Every DTO is mode:integration-test, amountBasis:isolated-test-plan, realPayment:false, orderPaid:false. A test status named succeeded is an outcome of this isolated protocol, never a paid customer/order. Legacy F2 payment_attempts and the F6 DB prohibition on attaching payments to integration orders remain intact. No financial/order/stock/promotion/shipment state is updated by a payment event.

## Provider-independent adapter

PaymentAdapter declares supported instruments (card, apple-pay, google-pay), merchant/account identity, submit, authenticated inspect, cancellation request and raw-byte webhook verification. These are BAZAR normalized contracts, **not a guessed provider wire/signature scheme**. A future approved adapter must prove account, environment, operation, currency/amount, authenticity and definitive finality according to that provider's actual contract.

Submission only acknowledges a provider reference; its response cannot mark a payment successful. Only authenticated inspect or verified webhook observations may set a definitive outcome. An inspect result must correlate to the requested operation. A webhook must authenticate exact raw bytes before JSON parsing and bind the configured account. We validate operation ID/reference, amount, currency, event ID and normalized state again in the service. The merchant account is snapshotted on intents/operations, included in the binding and scoped reads, and correlated through event/operation foreign keys. A valid event or resolver from another account cannot read or update an existing operation, even when adapter/provider names match. References are bounded opaque IDs; no provider payload, error string or credential is returned/logged.

The isolated helper uses an ephemeral random HMAC-SHA256 key, timing-safe comparisons and an explicit 5-minute signed timestamp policy. That algorithm/window/header is **test evidence only**, not a production default or merchant/provider selection. A real signature scheme, key rotation, event-time policy, canonicalization and replay semantics require the approved provider's documentation and security review.

## PostgreSQL, submission and double-execution protection

Only additive migrations are used: 0008 expands carrier constraints; 0009 adds payment_intents, payment_operations, payment_verified_events and payment_transition_audit. Existing migrations are unchanged. Intent/checkout/cart owner and version FKs correlate the test financial context. UNIQUE(checkout_id) and UNIQUE(cart_id) prevent a second draft from bypassing the same test-cart payment scope, including by editing its version. This is a conservative integration guard, not an approved production multi-order/seller policy. Replacing a changed financial basis or resetting/reusing this test-cart scope is deliberately unavailable pending approved purchase/cart lifecycle rules.

Creation locks actor/request key → owned cart → checkout → intent. It revalidates F6 stage, current prices/stock/address, acknowledged fingerprint, card-online selection and no unapproved promotion redemption. If an F7 selection exists, its shipping guard/current quote is mandatory. An existing intent must retain the identical synthetic amount/binding. A changed checkout/test basis fails closed.

Persist a submitting operation and request digest **before** calling submit outside the transaction. The durable operation UUID is the remote idempotency/reference key; one service submission is allowed per prepared operation. Replaying the actor/key returns historical/current state, never resubmits, and a changed request conflicts. A partial unique index permits at most one active-or-successful operation per intent (submitting, pending, unknown, succeeded); DB triggers reject forbidden transitions and direct terminal insertion. Separate checkout drafts for the same cart cannot create another intent, including after a version change.

If a submit times out, throws, acknowledges an invalid reference or fails to persist its acknowledgement, the outcome remains unknown or submitting. A crash in that gap is intentionally not called a decline. These states block another attempt, even with a different key. There is no blind resend, timeout reset, cleanup job or invented timeout-to-failure rule. Owner-scoped authenticated reconciliation can resolve the remote operation using the same durable ID. Provider-side idempotency guarantees and reconciliation for a production crash gap must be reviewed before activation; this code does not claim exactly-once delivery across an arbitrary remote provider.

State graph for the **test protocol**: submitting → pending/unknown; authenticated observations may move submitting/pending/unknown to pending, declined, cancelled or succeeded. Definitive final states are immutable. Identical terminal observations are idempotent; contradictory or out-of-order terminal events fail 409 and require reconciliation review. Submission alone cannot write a definitive status. A new operation is permitted only after an adapter has confirmed definitive decline/cancellation, with a new key and unchanged freshly verified basis. Unknown outcomes never permit retry. Production finality/late success/authorization-capture rules remain unspecified; the synthetic final-state model must not silently become financial policy.

Cancellation is a request, not optimistic local cancellation: inspect must confirm the remote result. A pending response or failed/uncertain cancellation remains non-retryable. It cannot cancel a succeeded operation. RefundAdapter is a future typed boundary only; no refund handler, eligibility, amount allocation, capacity restoration or simulated refund success is enabled.

Verified events are scoped by provider/account/event ID and a normalized digest, serialized before operation updates. Replays cannot update another operation or change payload/state. A conflict or mismatched amount/account/reference rolls back event/state together. Only bounded normalized facts/digests are stored, never raw webhook bodies, card/wallet data, signature keys or recipient PII. Trigger-generated audit rows cover creation and each state/version change with source and timestamp. Intents/events/audit are immutable; operations cannot be deleted or rebound to another owner/amount/provider. No production grants, real merchant or secret is provisioned.

## HTTP and Next.js

- GET/HEAD /api/v1/payments/capabilities: isolated methods, productionAvailable:false.
- POST /api/v1/payments/attempts: owned checkout/version/method/key; returns {attempt,replayed}.
- GET/HEAD /api/v1/payments/attempts/{id}: owner-only state, no shared cache.
- POST /api/v1/payments/attempts/{id}/reconcile or /cancel: empty object only; owner session/CSRF required.
- POST /api/v1/payments/webhooks/isolated: no browser-session substitute; raw body <=4 KiB / 2 seconds, validated content type/encoding and explicit test signature. Unknown webhook/provider paths are not activated. Receipt contains only test mode/replay acknowledgement, not customer data.

Session operations reuse F4 HttpOnly/Secure/SameSite cookies, exact Origin/Fetch Metadata and CSRF checks; mutations/search parameters reject unknown fields and unsupported methods. Logs contain only the static /api/v1/payments label, sanitized code/status and correlation UUID. No callback query/body or signature is logged.

PaymentBusinessClient is a separate opt-in same-origin typed transport with explicit CSRF, no redirects/cache/retries/fallback, response/time bounds, resource correlation and strict test-only outcome validation. It is not selected by demo checkout. Existing step 2 card-online/on-receipt, promo code and merchandise summary remain unchanged; no successful real-charge UI or card collection is introduced.

Wallet availability is capability-based, not an OS/user-agent guess. eligibleWallets requires secure context, an enabled future provider's method list **and** a successful browser/device SDK probe. Apple probe must use the approved merchant's Apple Pay JS availability flow; Google probe must use isReadyToPay with the provider-approved allowed methods. Missing/rejected probes or absent provider hide wallets. No arbitrary networks, merchant ID, SDK environment or tokenization scheme is chosen. The current demo has no enabled provider, so it does not claim live Apple Pay/Google Pay availability. Probe logic is tested independently from OS labels.

Primary references checked 2026-10-26: [Apple canMakePayments](https://developer.apple.com/documentation/ApplePayontheWeb/ApplePaySession/canMakePayments) checks device support, not necessarily a provisioned card; [Google isReadyToPay request](https://developers.google.com/pay/api/web/reference/request-objects) depends on configured allowed methods and its TEST behavior must not be represented as production readiness. Activation must review the current merchant/device/browser requirements.

## Verification and blockers

Tests cover signed success/decline, raw-body/key/timestamp failures, currency/amount/account/reference mismatch, repeated/concurrent events, cross-owner access, request replay, active/successful attempt exclusion, wallet retries after definitive decline/cancel, stale basis, timeout/unknown, persistence failure after remote acceptance, early webhook before acknowledgement, F7 freshness guards and F7→F8 schema upgrade. Typed client→authenticated HTTP→PostgreSQL and unchanged checkout regressions are required.

Before real payments: approve provider/merchant/legal/PCI scope, hosted/tokenized wallet flow and domains/certificates; authoritative final payable amount/currency/fees/tax/seller/promo/shipping policy; legal order/inventory lifecycle; actual webhook signatures/keys/account/environment/finality/event ordering; idempotency, cancellation/capture/refund and reconciliation semantics; production SMS/BFF/TLS, least-privilege grants, retention/audit/monitoring and controlled release. No real payment, real order, SMS, TTN, refund, deployment or merge is performed in F8.
