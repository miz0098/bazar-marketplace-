# ADR 0019 — F21 seller offers and ordinary storefront persistence

Status: approved business rule; implemented isolated integration, production activation blocked. Authority: explicit Phase F21 instruction. Supersedes the unresolved F20 catalog-card aggregation decision only; does not change financial rounding, payouts or legacy product DTOs.

One seller-owned purchasable variant is one offer/card. Its stable offer ID is the existing globally unique variant UUID, with product and seller relationships retained. No product cloning per card. Individual price, SKU, characteristics, availability and media are projected by additive migration0017. Search/filter/sort/pagination operate on offers. Cards link to the existing product handle with the exact variant query; no sibling/seller substitution. Old V2 parent price remains null when heterogeneous; that DTO is not a catalog card. The same model offered by multiple sellers uses independent seller-owned listings, not a fabricated shared ownership transfer.

The F21 isolated Next entry imports ordinary storefront pages/components and uses the existing F15 HTTPS gateway, F4 OTP/session, F9 cart and F13/F17 notifications. Both build/runtime flags, HTTPS loopback and Node-controlled disposable PostgreSQL are required. The ordinary production build rejects integration activation. No real SMS or UI OTP shortcut; test automation retrieves only its own live challenge through the existing protected helper. HttpOnly Secure SameSite Strict sessions, CSRF, Origin and owner checks remain intact. The production API composition does not expose these test authentication/private services.

An actor-bound observable memory store loads authenticated cart/wishlist from PostgreSQL. Focus/manual refresh reloads another device's changes. No realtime claim. Authenticated data is never serialized to guest storage. Separate guest storage contains only variant IDs and unit counts. Login selects the customer's server cart without copying, merging or replacing it. Logout revokes the session and restores only this browser's separate guest cart. Errors hide private state; no synthetic success. Durable existing cart receipts and version checks handle retries/concurrent mutations. Wishlist PUT/DELETE is set semantics under owner-scoped uniqueness.

Exact-offer wishlist is additive; old product-level wishlist rows remain intact and are reported as requiring explicit offer selection, never arbitrarily assigned. Unavailable offer rows remain saved; F20 binary availability is authoritative, not old stock fields. Restoration reuses F13 events/recipient uniqueness, including exact wishlist variants and existing cart/product-wishlist eligibility. No second notification subsystem or real push.

Only session/cart/offer wishlist are connected here. Other account screens remain explicitly preview workflows. F22 must connect ordinary checkout to approved multi-seller finance/shipping/payment lifecycle; F21 checkout is unavailable in the isolated entry, rather than falling back to synthetic completion. Production SMS/provider/grants, lawful privacy/retention and licensed import/media remain blockers. No seller dashboard, live commerce, merge or deployment is authorized.
