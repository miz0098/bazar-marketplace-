# ADR 0014 — F15 isolated HTTPS browser checkout

Status: isolated browser integration, not a production storefront switch or Demo100%. Base: merged PR #25, f2189894eacbd825406670888f8757cd2d8ceef5. [Acceptance](../F15_BROWSER_CHECKOUT_ACCEPTANCE.md).

## Separate artifacts and real server authority

The normal Next.js app, preview providers and API main retain their existing behavior. The new apps/storefront/browser-integration is a separate Next app/build root using existing styles, header/footer, typed API clients and a dedicated browser controller. Its next.config refuses ordinary startup/build without an explicit browser-integration flag. It is excluded from the normal app's TypeScript discovery; a separate typecheck/build validates it. The ordinary route tree contains no OTP/payment helper or integration route. API test gateway/adapters live only under tests, outside compiled src. The ordinary compiled API returns404 for helper/control paths and retains production503 guards for business modules.

The dedicated API entry requires NODE_ENV=test AND BAZAR_BROWSER_INTEGRATION=1, a runner-created capability/state file and a disposable loopback PostgreSQL URL. It cannot bind an external HTTPS origin. No environment flag enables test authentication, payment or shipment in API main. No paid service, deployment, DNS or autonomous OpenAI workflow is involved.

The runner builds the isolated Next artifact, creates a uniquely named pinned PostgreSQL Docker project and a temporary TLS key/certificate with loopback SAN. Each case gets a new random database and migrations, synthetic catalog/promo and F4/F7/F8 fixtures; previous case pools/API listeners close before replacement. No real database or application history is reset. The controller has a100-case safety cap (expanded in F16 for promo scenarios). The runner removes its child process groups, temporary keys/capability and container volumes when finished. Production credentials/data are never loaded.

The browser traverses catalog → product → guest cart → real F4 test OTP/session → explicitly added server cart → F12 owned address → F7 directory/selection/quote → F8 payment operation/verified signed event → F9 linked confirmation → F14 owned immutable history. This is browser-rendered UI with actual HTTP/PostgreSQL mutations, not page.evaluate creating a fake session or replacing network routes. Negative security tests also exercise raw browser requests deliberately. UI does not infer authentication from browser storage or Phase D preview.

## HTTPS and BFF boundary

The gateway binds only127.0.0.1 over HTTPS. Chromium trusts only the freshly generated certificate SPKI for this run; ignoreHTTPSErrors remains false and no global certificate-error bypass is used. Node control/readiness clients explicitly trust the ephemeral certificate with ordinary TLS hostname validation. No private key is committed or exposed by a route. This demonstrates the test boundary, not production domain/certificate provisioning.

The BFF uses fixed loopback API/UI targets, exact Host, Origin and Sec-Fetch-Site checks. Mutations require the configured HTTPS Origin. It rejects Authorization/Forwarded/x-forwarded-* instead of treating browser headers as trusted identity/client-IP assertions. API cookies are filtered to the F4 __Host session/flow names, kept browser-managed and never passed to the Next rendering upstream. Cookie responses must retain HttpOnly, Secure, SameSite=Strict, Path=/ and no Domain; the BFF neither manufactures nor weakens them. Reads preserve original Host/Fetch Metadata so F4 same-origin read verification remains meaningful; no fabricated Origin replaces a missing/malicious one. Native API CSRF/session/owner checks remain in place.

Upstreams are fixed, request headers/body/time are bounded by the gateway/native API, responses are no-store, and requests cannot select an arbitrary URL or user. Caching, shared-cookie bridges, credentialed cross-origin CORS and forwarded-client-IP trust are not introduced. Content security policy restricts connections to self; framing and external form submission are denied. The Next test build needs inline hydration/style allowances; this is not a reviewed production CSP/framework deployment.

## Test-only SMS/payment seams

The OTP helper exists only at the isolated gateway. It requires exact Origin/Fetch Metadata, the F4 signed flow cookie and CSRF, and a matching own challenge flow digest in PostgreSQL. It serves only an active unconsumed test-only delivery from the in-memory SMS adapter, never another flow's code. The UI explicitly labels it as an isolated OTP, not an SMS. Verification still runs the F4 server OTP HMAC/attempt/expiry/one-time/session rotation pipeline. The isolated registration checkbox authorizes fictional test participation only, not legal production registration consent.

The payment-result helper requires an authenticated owner session and CSRF. It accepts only the owned operation ID and an explicit synthetic success/decline choice, takes amount/reference/account from the server fixture, signs with a random test key and invokes the existing F8 webhook verifier. The UI re-reads the operation through the typed API; it cannot set succeeded directly or create confirmation from a client claim. Test DTOs continue realPayment:false/orderPaid:false. No PAN/CVV, real payment provider/SDK, financial invoice or remote request is created.

The administrative controller requires a random256-bit header capability, rejects all browser Origin/Fetch Metadata and is never served as UI data. Node-only commands create fresh cases or inject synthetic price/stock/carrier/SMS/revocation faults and read bounded database counts. There is no browser reset/fault endpoint with default credentials. Both helper and controller are absent from ordinary artifacts.

## Guest cart, resumption and three-step UI

The header receives optional presentation callbacks/count from the isolated controller; default ordinary header markup and behavior are unchanged. Auth context used to render the existing shell is never consulted as server identity. Product data/price/stock comes from PostgreSQL; missing media/ratings are not invented. The isolated product surface uses existing classes and a placeholder. Full catalog media/domain/pixel mapping remains a separate gate.

Guest cart keeps only bounded variant IDs locally. Logging in never copies them to the server: the newly verified cart is empty until an explicit add action. Server add/set/remove use current versions and idempotency keys, re-read actual prices/inventory and never submit a price. Existing normal storefront guest/demo cart remains intact with no merge policy change.

A bounded versioned sessionStorage record keeps only actor-bound opaque checkout/payment IDs, creation/confirmation idempotency intent, expected version and pricing fingerprint. It contains no price, contact, OTP, CSRF, cookie or authentication flag. Invalid/extra/oversized/cross-user data is discarded. Anonymous/revoked sessions clear the record; session restoration always calls the real server. Storage cannot authorize an order or validate a payment. On refresh, owned server cart/draft/operation/order/history are re-read. Confirmation intent is saved before posting, so retry uses the same exact key/input; immutable F9 links prevent duplicate orders. Post-order cart replacement/repeat-purchase and unknown financial-basis resets remain blocked by existing policy, not silently invented.

The approved three steps retain current checkout classes/structure: contacts+delivery, payment+promo+summary, confirmation. Contact display comes from the verified synthetic F4 profile/masked phone. F12 address creation uses owned opaque carrier/city/point references; no recipient PII is silently persisted or claimed ready for real shipment. NP, Meest and Ukrposhta use explicit normalized test adapters and available branch selection; BAZAR pickup stays disabled. Quotes are synthetic estimates with explicit technical expiry; current tariff/stock/price checks run before payment/confirmation. No live carrier response, tariff guarantee, locker capability or TTN is invented.

Server test amounts are displayed exactly in minor units without introducing financial rounding/allocation rules. Merchandise, delivery estimate and isolated payment plan remain distinct; no sum is presented as a legal payable total. A valid synthetic fixed promo can be previewed, but payment/completion with it remains policy-blocked. Removing it is an explicit user action. A no-promo success does not prove a discounted order.

Card is available only for the isolated protocol. Apple Pay and Google Pay remain visible but unavailable because no approved merchant/provider SDK/device probe is configured. Emulated iPhone/Android names are not wallet capability proof. Existing eligibleWallets contract/probe tests remain; actual compatible-device/provider wallet E2E remains blocked.

## Confirmation truth and remaining gates

A successful flow creates one F9 integration-test/pending record and completion link using a succeeded signed test operation. My Orders uses actual owned PostgreSQL list/detail/F14 audit, not fixtures. Real order payment remains not-initiated, delivery not-requested, inventory not-reserved, payable null and orderPaid:false. The browser labels the payment protocol evidence separately. No real order, inventory action, discount redemption, paid/cancelled/refunded claim or real notification is emitted.

Remaining: production HTTPS/domain/certificates/BFF/proxy/client-IP/rate/secrets/SMS and browser identity rollout; recipient/contact encryption/consent/retention; legal payable/tax/fee/seller/promo allocation/rounding/redemption/order/inventory/cart-after-order rules; real carrier/payment/merchant/wallet contracts and finality/reconciliation; actual lifecycle authorities/returns/refunds, privacy/grants/ops, full visual/manual acceptance and regular storefront server-mode mapping. F15 closes the isolated browser transport gap for the no-promo/card scenario, not every D05/I09 or production gate.
