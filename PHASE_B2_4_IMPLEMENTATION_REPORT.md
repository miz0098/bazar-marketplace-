## Shopify architecture and data contracts

Active `templates/product.json` selects new OS2 PDP/recommendation sections. Original Horizon product-information and recommendation sections, their nested blocks and settings remain **unchanged and disabled**, so they remain reviewable/recoverable. Other templates and the B2.1/B2.2 header/footer/home/catalog/search/card implementation remain byte-identical. The only shared native edit is a four-line rejection handler in `assets/product-form.js` described below.

The section uses global `product`, actual contextual `collection`, `product.media`, `product.options_with_values`, `selected_or_first_available_variant`, quantity rules, SKU, inventory policy and typed metafields. Breadcrumbs add an actual contextual collection only when Shopify supplies it; no guessed category/vendor hierarchy or URL. Standard product structured data is emitted from Shopify's `structured_data` filter.

Native `variant-picker` resolves `option_values` against Shopify HTML and publishes `ProductSelectEvent`. Public [Shopify variant documentation](https://shopify.dev/docs/storefronts/themes/product-merchandising/variants) was retrieved read-only (HTTP 200): impossible option-value combinations yield **null** for both `selected_variant` and `selected_or_first_available_variant`. This matches the local contract tested; it is not merchant-store testing. Initial first-available selection is Shopify's normal initial state, while explicit unavailable/impossible choices are never replaced with another purchasable variant. Fast-changing requests retain only the newest response. Combined listings, very high-variant catalogs and all Markets contexts still require actual-store acceptance.

`bazar-product` handles presentation, pending/failure guards and native events. It does **not** fetch or calculate an independent cart. Its capture-phase submit handler validates browser constraints and selection state, then calls native `product-form-component.handleSubmit`; omitting the separate `on:submit` binding avoids the native document-capture delegation running before the guard. Native `product-form.js`, `variant-picker.js` and `component-quantity-selector.js` are explicit imports through Horizon's existing import map. No global event rejection/suppression is installed.

A rapid-selection test exposed an existing native async `ProductSelectEvent` listener with `try/finally` but no rejection handler: aborting the previous request produced an unhandled `AbortError`. Add a narrow `catch`, ignoring expected aborts and warning on other failures, while preserving the existing generation guard/finally and every cart/quantity operation. The PDP's own failure handler keeps stale purchase controls locked. This is the only shared/native commerce logic edit; all old regression groups were rerun afterward.

Required-selling-plan products are explicitly blocked with pending-integration copy: no arbitrary plan ID or unimplemented plan-price promises. Quantity/price-break data remains Shopify-owned; B2B volume-tier presentation, app-required properties/bundles, gift-card recipient flows and specialized purchase applications require their own verified merchant integration. No silent custom-property/plan success is claimed. Current price is the selected variant base price, not a fabricated final cart total.

Without JavaScript, genuine gallery images/media posters and all content panels remain readable; a bounded native GET variant selector reloads the actual product URL, and the standard product POST remains usable. The fallback enumerates at most 250 actual variants with an explicit notice above that number; the JavaScript path uses native option-value lookup and does not rely on that list. Full no-JS high-variant selection is a documented limitation.

## Editor configuration and integration boundaries

The new PDP section exposes optional richtext information plus configurable `namespace.key` fields, defaulting to `custom.specifications` and `custom.additional_information`. Only `rich_text_field`, `multi_line_text_field`, `single_line_text_field` are rendered; absent/unsupported values remain hidden. No metafield definition/content, app, menu or merchant resource was created. Richtext is rendered through native `metafield_tag`; plain text is escaped. Product description is trusted merchant Shopify HTML, as in native Horizon.

The static options block is the existing `variant-picker` with its settings/editor attributes and actual swatches enabled where available. App blocks render through standard OS2 `render block`; review/Q&A installation/functionality is not simulated. Recommendations expose a bounded count (2–10, default 8) and the shared card mode. Static card block settings are copied from the original native recommendation section; no parallel product-card system is added. Real editor add/save/reorder/static-context behavior remains a remote acceptance item.
