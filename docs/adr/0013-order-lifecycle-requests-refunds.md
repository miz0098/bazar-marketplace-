# ADR 0013 — F14 order lifecycle, returns and refund foundation

Status: bounded customer preview plus isolated PostgreSQL/HTTP protocols. No real cancellation, return logistics, legal eligibility, payment or refund activation. Base: merged PR #24, 1cf6e2a335ab329ec2260226377d0e3ec4e1d21a. [Acceptance](../F14_ORDER_LIFECYCLE_ACCEPTANCE.md).

## Separate status axes and immutable order facts

F6/F9 integration orders stay immutable pending records: payment not-initiated, delivery not-requested, inventory not-reserved, payable/delivery amounts null and orderPaid:false. F8 signed synthetic success is not a paid order or a real confirmed purchase. F14 does not update those facts or weaken their guards. Its separate request, history and refund-attempt tables extend an owned order without rewriting the checkout snapshot. Actual order/payment/shipment/return/refund transitions are separate authorities; none confirms another.

New ordinary /api/v1/order-lifecycle routes return 503. The service constructor requires NODE_ENV=test and explicit isolated policy/adapter scopes; HTTP injection also refuses ordinary config, and main selects neither. F4 verified principal, exact Origin/Fetch Metadata, CSRF, bounded body/time, no credentialed CORS, strict fields/IDs/quantities and sanitized static logging remain intact. No caller owner, price, status, provider or contact override is accepted. Foreign and missing order/request IDs share 404. Legacy rows are not relabelled: only F6 integration orders with verified immutable snapshots are read.

GET/HEAD /api/v1/order-lifecycle/orders reuses the F6 owned list and owner/limit-bound cursor (default20/max100); GET/HEAD /orders/{id} returns five separate status axes, source line IDs and immutable prices, explicit request eligibility, requests/refund protocol state and chronological audit. This is an opt-in sidecar contract, not a replacement for the existing /orders DTO. Details cap lines at100 and requests/refunds/history at200, fail503 on overflow and never silently truncate. Pagination/operational limits beyond those technical bounds require review.

## Request-only cancellation and returns

POST /orders/{id}/cancellations accepts idempotencyKey/reason. POST /orders/{id}/returns adds nonempty distinct owned orderLineId/quantity items. The default policy is absent: eligibility says policy-required and creation fails CHECKOUT_POLICY_REQUIRED. An explicit isolated canRequest callback enables request-only tests; false says unavailable. These are not legal return rights, automatic cancellation or approval. No production deadline, exception, shipping label, fee or seller authority is invented.

Actor/order/kind/canonical input digest protects replay. The owned order row serializes distinct operations; unique actor/key and one cancellation request/order block duplicates. Same key/input returns current owned state without another request/audit; changed input conflicts. Return items are checked against owned purchased lines, bounded positive integer quantities, and cumulative claims under the same order lock. A SQL trigger repeats the ownership/kind/cumulative check and accepts items only in the request's creating transaction; items cannot be updated/deleted or appended after commit. A deferred check requires nonempty return items. Failed item insertion rolls back request, key, history and notification atomically.

Request tracking uses requested → under-review → closed-for-test only. closed-for-test is a technical test closure, NOT approved, cancelled, received, restocked or refunded. reviewForTest requires an explicit isolated canReview policy, owner/order/request checks and expectedVersion; no staff/review/status HTTP endpoint exists. Repeated same transition/version does not duplicate audit; conflicting/stale/reverse/shortcut transitions fail. Actual order state remains pending. Staff/seller roles, assignments, approval reasons, authority, refusal/withdrawal/reopen, consent and legal treatment remain blockers.

All return quantities remain conservatively claimed even after test closure. No automatic release, second shipment or entitlement reset is inferred. This is a test integrity boundary; production release/withdrawal/replacement rules must be approved separately.

## Refund protocol and capacity

Refund is independent from item-return state. Only internal prepareRefundForTest can prepare an attempt; customer HTTP has no amount/refund mutation route. It requires an owned return request, an immutable F9 order/payment completion link, the same owner's succeeded F8 operation and stored authenticated payment evidence, matching adapter/account/currency, plus an explicit server-only isolated refundPlan. A plain F6 record, unlinked/synthetic legacy payment or missing financial plan is blocked. Nothing here makes the F9 proof a real payment.

The plan supplies a positive safe-integer amount/currency/revision; no browser amount or automatic merchandise/shipping/discount calculation is used. scope is always isolated-test-plan. Full means the original synthetic payment amount with zero prior claims; partial must be strictly smaller. The payment row lock and SQL trigger enforce sum(all claims) ≤ confirmed test operation amount. Unique request and actor/key prevent a second refund for the same return or replay; different requests still share the same locked capacity. Identity/amount/currency/basis/account and the explicit server-plan revision are stored immutably for audit.

All prepared, pending, unknown, confirmed-for-test and rejected-for-test claims conservatively retain capacity. Unknown/timeouts never become failure/success or permit blind retry. No amount is released or reallocated without approved financial rules. This is deliberately narrower than a future provider workflow; partial retries, multiple attempts, restorable capacity and allocations remain blocked.

The adapter authenticates raw bytes before parsing; service revalidates exact event keys/UUIDs, refund/payment IDs, account, amount, currency and allowed normalized state. Verification is bounded to2s/4KiB. No selected production signature scheme, merchant or provider transport exists. The only HMAC/time-window implementation is an isolated random-key tests/helpers fixture, excluded from src build. No browser-facing webhook handler is enabled; FutureRefundProvider prepares the later server boundary only.

Prepared may receive authenticated pending/unknown/confirmed-for-test/rejected-for-test observations. Pending/unknown remain reconcilable; definitive test states cannot reverse. Same provider/account/event digest replays once; mismatched payload/rebound IDs/amounts fail and roll back. A new equivalent terminal event may be recorded without another state transition. Receipt, state/version and trigger audit commit together; audit failure rolls back the receipt, allowing safe retry. No real submit/refund is performed.

Every refund DTO says realRefund:false and fundsReturned:false even after confirmed-for-test. The order remains unpaid/unfulfilled according to F6. Reaching a test protocol terminal state is not evidence that actual money moved. Real provider capture/settlement/refund finality, signatures, reconciliation and authenticated operation linkage require review before any financial activation.

## Additive schema and immutable audit

Migration0013 leaves0001–0012 byte-unchanged. Adds request/return-item/refund/evidence/history tables, owner/composite FKs, unique keys, bounded minor amounts and versions, capacity/transition/deferred completeness guards and indexes. All request payloads, line claims, provider evidence and history are immutable; status-only updates require the guarded source/version/graph. Initial pending history is backfilled from immutable F6 orders with their original timestamps; an additive insertion trigger records new test orders atomically. Request/refund state changes are trigger-audited, independent of application success responses. No real contact/card/provider credentials or event seed is installed. Runtime grants, migrations and privacy release remain separate approvals.

## F13 integration without fabricated business events

Extends the typed future notification envelope and database kind constraint with return.requested and return.status_changed. Only actual isolated return-request insert/review writes those metadata inbox events, atomically with its audit. They describe a test request, not received goods or an operator response. No channel dispatcher, consent assumption, email/SMS/push, new notification UI or real delivery is activated.

FutureOrderLifecycleEvent prepares order.status_changed/order.cancelled/return.requested/return.status_changed/refund.completed linkage. Actual order/cancellation/refund emitters remain disabled: closing a cancellation request does not emit order.cancelled; confirmed-for-test does not emit refund.completed. F6/F9 pending/synthetic records never become real paid/cancelled/refunded notifications.

## Storefront preview and blockers

Existing orders list/filter/detail and account navigation/layout are preserved. The detail main column reuses current card/form styles for five distinct status labels, cancellation availability (policy-required), a clearly fictional snapshot/request history, quantity/reason selection, demo-return request and its status. No sidebar section, provider mapping, real cancellation button or refund form is added. Profile fixture order labels remain demo; payment/delivery are unverified independently. A request never changes order status.

The account service composes an in-memory lifecycle helper. Its actor-free mock uses owned fixture IDs only and validates quantities/replay; it is not the API authorization layer. Requests survive client navigation within the preview instance and reset on refresh, with visible copy. No reason, request, contact or financial data is written to local/session storage. F12 wishlist IDs and demo checkout persistence remain separate. Immediate duplicate submit is guarded before rerender; errors retain drafts; keyboard focus, white/empty/error/loading and desktop/mobile/axe/overflow checks apply.

The separate typed Next.js OrderLifecycleClient uses same-origin browser cookies, closure CSRF, bounded JSON/time, strict mode/scope/DTO validation, no redirect/cache/retry/fallback. Existing demo providers do not select it; no production auth bypass or browser BFF is added.

Unresolved: authoritative order terms/numbering/tax/payable/inventory/cart/promo lifecycle (ADRs5/6/10); cancellation allowed states/automation/authority and stock/promo/payment effects; legal return windows/exclusions/reason taxonomy/partial quantities/approvals/reopen; carrier reverse logistics/cost/condition/receipt inspection; discount/unit/seller/shipping/tax/fee allocation, rounding, full/partial refund entitlement and capacity release; provider capture/refund/account/finality/authenticity/reconciliation; staff roles, customer consent/privacy/encryption/retention/deletion, production SMS/BFF/TLS/grants and UI/server mapping. No defaults are invented. These remain blockers for real operations, not permission to call Demo100% or Production Ready.
