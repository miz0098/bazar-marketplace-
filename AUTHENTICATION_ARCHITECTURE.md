# BAZAR.UA — Authentication architecture (Phase B1)

Evidence reviewed 2026-11-02. **Recommendation: architecture A**, Shopify Plus + an independent external OIDC provider, with phone/SMS as the returning-user interaction and a real verified-email enrollment gate before Shopify account provisioning/linking. This is conditional on merchant Plus entitlement, an appropriate provider and explicit approval of the email UX change. No production authentication is implemented. Plus is selected, not verified active.

Phase A input: [PR #41 authentication findings](https://github.com/miz0098/bazar-marketplace-/blob/2e901f8aaeb1166ff0827eb63a6363ed18c9c437/SHOPIFY_RESTORATION_AUDIT.md), [plan](https://github.com/miz0098/bazar-marketplace-/blob/2e901f8aaeb1166ff0827eb63a6363ed18c9c437/SHOPIFY_RESTORATION_PLAN.md), [design conflicts C5/C9/C10](https://github.com/miz0098/bazar-marketplace-/blob/2e901f8aaeb1166ff0827eb63a6363ed18c9c437/DESIGN_REFERENCE_MAP.md). ## What Shopify actually requires

Shopify's [external-provider requirements](https://help.shopify.com/en/manual/customers/customer-accounts/sign-in-options/identity-provider/requirements) establish: Plus; authorization-code flow (not implicit/hybrid); PKCE for public clients, including mobile S256; RP-Initiated Logout (not front/back-channel logout); authorization/token/JWKS/discovery endpoints; token/discovery/userinfo response within one second; required subject, nonce, issuer, audience and verified-email claims; asymmetric token signing, not HS256; refresh-token support for longer sessions. These are documented capabilities, not BAZAR integration test results.

**Exact email consequence:** Shopify needs a unique real email and boolean `email_verified: true` from the IdP. Successful SMS possession verification does not verify an inbox. A phone-only IdP profile cannot complete this contract. An Entra `upn` exception is not a general phone/no-email workaround and still requires a valid reachable address. There will be no generated substitute addresses, false verification or Firebase Authentication.

An email field can remain absent from the initial phone screen, and need not be requested again on ordinary returning logins after verified enrollment. It **cannot remain optional for someone entering Shopify-linked accounts via A**. Before that boundary, the customer can browse/shop as a guest, or use separately authorized BAZAR-only services if separately approved; do not label that state Shopify-authenticated. Guest checkout's contact settings are distinct from OIDC provisioning and require their own merchant proof. Email OTP architecture C also requires email. Only B preserves fully optional email for BAZAR identity itself, at the cost of divided account/checkout identity.

Duplicate sign-in and merge/recovery friction. | Email → six-digit emailed code → Shopify session; phone collected separately, with separate SMS verification if phone ownership required. No passwords. |
| Email | Required and verified at Shopify enrollment; optional before it. | Optional in BAZAR; required to enter native email-OTP Shopify accounts. Guest checkout contact policy is separate. | Required and verified through native email OTP. |
| Security | Managed OIDC verification, durable subject mapping and dual-proof enrollment; remaining risk from SIM-swap/recycled numbers and bad account linking. | BAZAR bears OTP/session/recovery and authorization security. No external IdP required. |
| Known limitation | Cannot deliver optional-email Shopify SSO; IdP session is not automatically a BAZAR API access token. | Cannot promise unified Shopify account/checkout login; not a stealth SSO replacement. | Does not preserve approved primary phone/SMS interaction. |

Choose A for the most faithful supported unified customer identity, **not because optional email is solved**. If verified-email enrollment is rejected, A is blocked; choose B with explicit UX boundary approval or C with explicit primary-login change approval. Do not silently switch architecture. No IdP or paid SMS vendor is purchased/selected by B1.

## Proposed A enrollment and account linkage

1. Normalize Ukrainian phone input to E.164 `+380` plus nine national digits; validate actual supported mobile numbering with an updated library/provider lookup, not regex alone. Do not infer carrier from prefix due to number portability.
2. Begin an IdP transaction bound to state/nonce, PKCE verifier and a short-lived browser transaction. Send a six-digit challenge using a contracted SMS provider only in a later authorized phase. Never log OTP or return it to the theme.
3. Validate an unexpired, unused challenge with atomic consumption. Rotate server session identifier after verification; this yields only the permitted IdP/BAZAR state, not proof of Shopify login.
4. For new/unlinked customer require **actual inbox verification** before issuing the Shopify OIDC authorization result. Use an unguessable, single-use, expiring email verification transaction, bind it to the current user and prevent arbitrary metadata from setting `email_verified`. Do not collect passwords. Link an SMS connection to the verified-email profile only after proving both belong to the same person; preserve the canonical subject through future logins.
5. Shopify matches email to an existing customer or creates a new customer on successful sign-in, then links the subject. This behavior is documented in [connection and account management](https://help.shopify.com/en/manual/customers/customer-accounts/sign-in-options/identity-provider/connect). Preflight collisions, mismatched-subject errors and historical duplicate customers. Never overwrite a subject to resolve a conflict automatically. Merchant-assisted unlinking needs verified ownership and an audit trail.
6. Store `(issuer, immutable sub) ↔ BAZAR customer ID ↔ Shopify shop/customer GID`. Phone/email are mutable attributes, not primary keys. Shopify callbacks/session establishment must complete before UI claims Shopify access.
7. Provision independent API entitlements only through an authenticated server flow with correct issuer/audience/resource ownership. An IdP ID token for Shopify is not a general API bearer token; issue/validate the intended API-audience token or establish a secure BFF session. The server fetches only that principal's orders/addresses. Reviews, wishlist/support are independent API resources.

Provider implementation must prove a single canonical identity can retain both verified email and SMS-primary login without creating a new subject per connection. [Auth0 SMS passwordless](https://auth0.com/docs/authenticate/passwordless/authentication-methods/sms-otp) supports Twilio/custom phone providers, but its SMS connection is not by itself verified-email Shopify provisioning. Treat Auth0 as a candidate managed IdP, not a pre-certified BAZAR solution. Self-hosted OIDC reduces vendor dependence but adds custom SMS flow maintenance, signing-key custody, upgrades, high availability and the one-second endpoint requirement. No existing BAZAR demo source is an approved IdP.

## Session, refresh, logout and checkout continuity

There are separate IdP, Shopify Customer Accounts, theme/browser, independent API and Flutter credentials. No shared parent-domain cookie should grant seller/staff access. Use Secure/HttpOnly, narrow scope, SameSite appropriate to the callback, CSRF protections and server-side transaction state; use OS secure storage on mobile. Never persist bearer/refresh tokens in localStorage or leak them in URLs/logs.

Shopify documents customer sessions up to 90 days, subject to IdP token lifetimes; lack of refresh token can shorten effective login to the access-token lifetime. Request/configure refresh-token issuance as supported by the IdP (often `offline_access`), rotation/reuse detection/revocation and bounded lifetimes. “Up to 90 days” is not a promise of a 90-day session for BAZAR. Test expiry, clock skew, revoked refresh token, key rotation and concurrent sessions.

Use the registered RP-Initiated Logout endpoint and exact post-logout allowlist; end BAZAR server session, revoke eligible tokens and clear local app credentials. Front/back-channel logout is not supported by Shopify's documented external-IdP contract, so do not promise instant global logout on all devices. Define whether user logout is current-device or all-devices, and test Shopify/IdP/API state independently. A local UI logout is insufficient.

For web OS2, prove hosted Shopify account login → return to storefront → cart → checkout → order history on the same intended customer. For Flutter, use Shopify Customer Account API public-client authorization-code + S256 PKCE in a system browser with app/universal links, state/nonce and allowlisted callbacks; never embed a confidential client secret or intercept native payment UI. See [Customer Account API authentication](https://shopify.dev/docs/api/customer/latest).

Keep these client registrations separate:

| Protocol leg | Client and credential boundary |
|---|---|
| Shopify Customer Accounts → external IdP | Shopify is the confidential OIDC client; register its exact callback/logout URLs and server-held secret, with documented `client_secret_basic` token authentication and `openid email` scopes. |
| Flutter → Shopify Customer Account API | Flutter is a public client with its own approved redirect/app-link registration and S256 PKCE; Shopify controls customer authorization and can delegate the hosted sign-in to the external IdP. No confidential secret in Flutter. |
| Flutter/web BFF → independent BAZAR API | Obtain an API-audience access token or server session through the approved BAZAR/IdP client. Keep this independent from a token intended for Shopify; shared subject linkage does not make tokens interchangeable. |

For a Storefront API cart, attach a **Customer Account API access token** to cart buyer identity using `cartBuyerIdentityUpdate`/cart creation as documented for the selected API version, then use its `checkoutUrl`. An arbitrary BAZAR JWT or IdP ID token is not interchangeable. Shopify also documents browser-session silent SSO via `sso=silent`; this does not log in a browser that lacks an eligible session. See [checkout SSO clarification](https://shopify.dev/changelog/posts/headless-checkout-sso-is-now-documented-with-ssosilent). Mobile browser/webview cookie isolation, consent, return paths and eligible wallet behavior require device proof. Flutter is compatible at protocol level; no Flutter SDK integration has been tested here.

## Recovery and phone change (proposed controls, not Shopify defaults)

Phone change requires recent authentication, proof of old and new number when available, cooldown/risk review and notification to existing verified email/phone. Preserve subject/customer/order linkage; revoke sessions/refresh tokens according to risk policy. Losing a phone requires proof via previously verified recovery channel or reviewed support process; knowing order number/address/phone alone is insufficient. A recycled number must never inherit another customer's orders. Step up with verified email for high-risk login/change, and document that this can add friction beyond the normal SMS-only returning flow. Email changes need a newly verified inbox and controlled Shopify linkage update. Account deletion must address IdP/API/Shopify data independently with legal retention rules.

## SMS delivery and OTP security

Twilio publishes [Ukraine SMS support/guidelines](https://www.twilio.com/en-us/guidelines/ua/sms); that is evidence of a documented route, not BAZAR sender approval or delivery success. Confirm sender identity, transactional content, Ukraine geo-permission, country/account restrictions and coverage with provider. Validate Kyivstar, Vodafone Ukraine and lifecell, roaming/ported numbers, latency/delivery receipts and Unicode segmentation in an explicitly authorized later delivery test. No paid SMS or real customer OTP was sent in B1. A local Ukraine aggregator can be evaluated against the same contract; none was verified as configured.

Proposed baseline for review: six random decimal digits, five-minute maximum TTL, five failed attempts per challenge, at least 60 seconds between sends, layered per-number/device/IP/prefix hourly limits, a global spend ceiling and anomaly alerts. Tune actual numeric thresholds against provider capabilities/risk; they are **BAZAR proposals**, not claimed Shopify defaults. Enforce on the server/provider, invalidate superseded challenges, bound resend count, use generic responses to avoid enumeration, rate-limit verification separately and atomically consume successful codes. Hash/HMAC challenges if independently stored, compare safely, never store/log plaintext OTP, bind to purpose/transaction/phone, prevent code re-use and authorization-code/nonce replay, and audit without retaining sensitive payloads. SMS is not phishing-resistant; address SIM swap, recycled-number and pumping risk. Do not block recovery permanently through an attacker-triggered account lock.

## Cost model and evidence

Budget per month as `Plus contract + IdP tier/MAUs + SMS attempts × destination rate + successful verifications × verification fee (if used) + email + hosting/security/observability`. [Twilio Verify pricing](https://www.twilio.com/en-us/verify/pricing) advertises $0.05 per successful verification **plus channel charges**; Ukraine SMS charges must use the actual destination route, not US example rates. [Auth0 pricing](https://auth0.com/pricing) varies by MAUs/features; confirm SMS, custom provider, account linking, refresh and production support tier in a written quote. No BAZAR subscription amount, SMS unit quote or usage volume was supplied, so no reliable total is claimed. Architecture C avoids external IdP/SMS recurring expense for login, but sacrifices the approved primary interaction.

## Local proof and blocked integration tests

[Offline contract experiment](analysis/shopify-plus-b1/README.md) ran 26 tests using only in-memory signing keys and protocol fixtures. It rejects missing/unverified email, invalid issuer/audience/nonce/time/algorithm/signature and unverified Plus configuration. It never issues a session or connects to Shopify/IdP/SMS. Signed `email_verified=true` only establishes that a claim was signed by a trusted local key, not actual inbox verification. Nonce mismatch is tested; distributed one-time nonce/code consumption, issuer discovery, key rotation, recovery, OTP transport and refresh/logout are **not implemented or tested**.

Blocked: merchant Plus/account configuration, IdP discovery/latency/connection test, real enrollment/linking, SMS deliverability, refresh/revocation/logout, web checkout continuity, Flutter browser/deep-link/token flow and cross-user account authorization. Required access: merchant-owned non-production Plus-enabled store and collaborator permissions, test IdP/client/callback metadata, SMS/email sandbox/test facility with no paid sends under this scope, Customer Account API public-client configuration and approved test devices. Actual paid SMS, real customers/orders or activation still require separate authorization.
